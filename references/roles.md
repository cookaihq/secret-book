# 本次角色与首次使用

整套 Skill 安装完成时，先执行“安装完成后的角色选择”。日常添加、设置或配置凭证先完成“明确配置需求”，再读“确定角色”和“检查实际状态”，进入当前角色对应部分；中断续轮还需读“恢复”。本文件是四类角色执行规范的维护入口。角色表示任务职责，不授予飞书权限，不替代对象、身份、记录或具体写入确认。

## 安装完成后的角色选择

整套 Skill 安装成功后，在收尾回复中按以下顺序引导；已有表或登录配置也要说明四种用法。

1. 简短报告实际安装版本、位置，以及当前宿主发现／调用和依赖检查的结果，未验证项如实说明。
2. 在回复正文完整介绍下表中四个角色的用途和“如何开始”，使用日常语言，不只列角色名称或让用户自行翻 README；脚本角色值仅供内部执行。
3. **介绍之后再让用户选择**：“你这次想以哪个角色使用 Secret Book？”提供“令牌表管理员／凭证提供者或维护者／凭证使用者／业务 Skill 或 Plugin 接入开发者”四项。宿主支持四项选择时使用选择控件，否则列出 1–4，让用户回复编号或角色名称。
4. 等待用户选择后，再读对应角色部分并检查实际状态，按“记录任务与执行”继续；新建脚本任务时使用所选角色和 `--basis explicit`。未选择或暂不使用时停在安装完成，不发起登录、建表、接管或凭证配置。续轮收到选择时重新读取本节；本次选择不设为永久默认角色。

这是整套 Skill 安装完成后的收尾步骤。日常调用、更新或已有业务任务中补装依赖，按下方角色优先级继续，不重复要求安装后的选择。

## 明确配置需求

这一步适用于添加、设置、配置、保存 API Key／凭证的需求，覆盖维护记录和为业务工具取用两条流程。单独列记录、查看连接等目标已经明确的查询仍按原动作执行。

1. **从用户的请求和已确认上下文确定配置依据。** 使用对象是具体的 Skill、Plugin 或项目；服务名称、表链接、当前目录、已安装的同名插件或唯一候选记录，都不能单独证明用户选择了哪个对象。明确的业务调用可以沿用实际调用方；角色、账号或表的确认不代替对象选择。
2. **对象和确切配置均未明确时，先让用户选择并等待答复。** 例如收到“〈表链接〉设置 AI Hub 的 API Key”，下一条业务回复应为：“这个 Key 要用于哪个 Skill、Plugin 或项目？你可以选择：① 指定使用对象，告诉我名称或路径，我来分析配置要求；② 直接提供确切配置：name、service、purpose、secret，Value 可以稍后补。”此阶段的读取范围是 Secret Book 自身流程和已有用户上下文；候选对象的 README、声明、配置代码和加载器等用户选定对象后再读取或运行。不查表选凭证，也不创建带有猜测对象的业务任务。用户选择对象路径但尚未指明具体对象时，继续取得名称或路径。
3. **用户已明确对象时，直接分析该对象。** 读取其实际配置说明、声明或加载器，核对真实字段、格式及用途，把分析结果交用户确认；无需再次询问对象。用户只确认对象不等于已确认分析出的记录方案或写入目标。无可靠配置依据时说明缺口并补齐。
4. **用户选择确切配置时，只按其提供的信息整理。** 收集 `name`、`service`、`purpose`、`secret`，也可从自然语言回复整理成一组候选内容让用户确认，明确指出缺项或歧义。Value 可以留空；此路径不需要发现或分析候选使用对象，不额外读取候选产物的配置说明或代码。尚未选择路径时，不能替用户填一组默认字段，把字段确认当成对象选择。

配置依据明确后再按实际任务进入对应角色。新增记录沿用下方维护者流程：确认四项方案后由 Agent 创建记录，用户只补缺失的 Value。用户明确要求为业务对象取用已有凭证时，按使用者流程确认实际记录、字段映射和文件；尚不明确是新增记录还是取用时，补问这一动作，不自行改成给某个插件写本机配置。

## 确定角色

安装收尾按“安装完成后的角色选择”由用户选择；日常配置需求先满足上节条件，再按以下优先级确定本次角色和目标：

1. 用户明确指定的角色。
2. 同一未完成任务已经确定、且仍符合当前目标的角色。
3. 使用对象／配置要求和任务含义已明确时，由 Agent 判断并说明角色。例如用户已明确给某个 Plugin 配置已有凭证，可以说明“本次按凭证使用者处理”。无需为角色判断再等待一句“确认”；这不授权推断尚未确定的使用对象。
4. 任务含糊或与角色冲突时，让用户选择“管理令牌表／维护凭证记录／取用凭证／开发业务接入”，再执行依赖该选择的动作。

| 角色 | 怎样使用 Secret Book | 如何开始 | 脚本角色值 |
| --- | --- | --- | --- |
| 令牌表管理员 | 创建令牌表、检查或补齐表结构、安排协作者权限 | 说明要新建表还是管理已有表；已有表提供链接，确认本人账号和具体操作后处理 | `administrator` |
| 凭证提供者／维护者 | 在已有表中登记和维护凭证、用途及可见人员 | 取得表链接与编辑权限，明确使用对象或配置要求，由 Agent 创建记录；缺少的密钥值在已有记录中补填 | `maintainer` |
| 凭证使用者 | 取用已有凭证，为业务工具配置 Key，或临时执行／复制 | 提供表链接及工具或用途，用本人账号只读连接；确认记录、字段和保存位置后取用 | `consumer` |
| 业务 Skill／Plugin 接入开发者 | 为自己的工具实现 Secret Book 配置保存和修复接入 | 提供代码和配置说明，先做本地实现与模拟验证，无需先准备真实表或登录 | `developer` |

“给这个 Plugin 配好 Key”属于使用者；“为我开发的 Plugin 实现 Secret Book 接入”属于开发者。配置名称“工作／个人”、当前飞书账号、记录中的业务 `account` 与任务角色相互独立。配置盘点和切换是公共操作，不自动判成管理员。

用户明确要求跨职责操作时，依次说明并切换任务角色，复用已有授权；缺表、缺记录或无权限本身不能触发角色升级。任务完成后关闭待办，不设置永久默认角色。Agent 规则只引用本入口，不复制四套流程。

## 检查实际状态

只检查当前目标需要的条件；解释、飞书界面填写指导和本地接入开发无需先登录。

| 观察到的情况 | 下一步 |
| --- | --- |
| 当前宿主未发现 Skill，或脚本与 SKILL.md 版本不一致 | 核对实际安装路径与版本，按已获授权的安装／更新范围修复 |
| 任务需要脚本但 uv 不可用 | 按 SKILL.md 的命令入口准备 uv |
| 安装／补齐依赖或访问飞书时缺少 lark-cli | 按 [Lark CLI 依赖自动准备](../SKILL.md#lark-cli-依赖自动准备)直接安装、复检并继续，不另问安装方式；仅本地开发不要求 lark-cli |
| 需要访问飞书，尚未选定账号、没有有效身份或希望登录其他账号 | 按 [飞书账号选择与登录](../SKILL.md#飞书账号选择与登录)展示账号选项，再完成登录与实际身份确认 |
| 所有适用配置层都没有连接 | 按下列角色进入首次使用 |
| 配置部分缺项、格式损坏、旧格式、身份不符或被覆盖 | 报告证据并修复原来源，不当成新安装覆盖重建 |
| 表缺列、记录缺 ID、无可见记录或权限不足 | 分别交管理员、维护者或实际权限管理入口处理，不旁建新表 |
| 业务工具已有可用本机配置，用户只是正常运行业务 | 交回业务流程，无需为了运行补装或初始化 Secret Book |

全局 `.env` 不存在、为空、仅含更新开关，或 `config list` 没有条目，都不足以证明本机没有连接。核对实际工作目录的进程环境、`.env.secret-book`、`.env.local`、`.env`，以及本次明确启用／选择的全局配置。完整的高优先级资源组优先；部分组报错，不跨层补齐。原生 Windows 与 WSL 按各自运行环境和个人目录检查。

换电脑或重装后复用已有表，先只读连接同一张飞书表，再经确认保存本机连接；该目标本身不包含接管或补列。表与创建时的电脑系统无关，本机依赖、登录和配置按当前实际运行环境检查。通用引导使用“当前电脑”“已有令牌表”；只有用户明确提供或本轮核实了相关设备信息时，才具体称为 Mac、Windows 等，当前环境也不能证明原电脑的系统。

飞书身份复用 SKILL.md 的两阶段确认：展示 profile、应用、用户名与用户标识，确认后固定身份；每次访问前重新核对。共享表成员使用自己的 profile，不复制管理员的身份固定值或登录凭据。

## 记录任务与执行

需要运行脚本时，在真实业务工作目录执行以下命令，统一加 SKILL.md 中的 `uv run --project` 前缀。
纯说明、飞书界面填写指导和未涉及脚本的接入设计可直接进行，不以缺少 uv 或登录为由阻塞。

1. 先用 `workflow status --agent <实际宿主>` 检查未完成任务，只复用目标与当前请求一致的那一项。多项无法确定时让用户选择；不能把其他任务的角色当成默认角色。
2. 配置依据与本次目标明确后，新任务用 `workflow start --role <角色值> --basis explicit|inferred --goal <不含密钥的简短目标> --agent <实际宿主>`。用户指定角色用 `explicit`，Agent 判断角色用 `inferred`；Agent 自行写入的 goal 或 basis 不能作为用户已选择对象的证据。返回 `task.id`；未传角色时返回 `role_required`，不发起登录。
3. 本任务内的业务命令都追加 `--workflow <task.id> --workflow-agent <实际宿主>`。CLI 校验任务角色和宿主／目录／安装；原有直接 CLI 调用保留兼容，此校验是任务路由，不是飞书权限控制。
4. 待确认时展示本次输出的完整摘要；续轮用 `workflow status --id <task.id> --agent <实际宿主>` 恢复。确认后用原参数和该任务最新的 token 继续：身份用 `--confirm-identity`，业务写入和 ID 修复用 `--confirm`。输入变化、身份变化、跨任务 token 均要求重新预览。
5. 成功完成本次目标后执行 `workflow finish --id <task.id> --agent <实际宿主>`。用户取消或放弃该操作时追加 `--outcome cancelled`；不会删除表、撤销写入或把角色延续到新任务。

宿主名称从当前会话取得，例如 `claude-code`、`codex`、`workbuddy`；不是根据哪个目录存在推断。
`workflows.json` 位于 Secret Book 个人配置目录，使用与其他本机状态相同的锁、原子替换与文件权限。
`status` 只读状态，不访问飞书或执行待确认动作；`config list`、`list/get`、`configure-status` 等诊断不会清掉原待办。

## 令牌表管理员

1. 明确是新建、接管已有表，还是仅讨论方案。仅说明角色不构成建表授权。
2. 需要操作时准备依赖，选择 profile 并登录，展示实际飞书身份取得确认。
3. 新建使用 `init-create`；已有表先用 `init-connect --url <表链接> --lark-profile <本人profile>` 只读检查，展示缺列等差异，用户已授权接管或补列后执行 `init-adopt`。字段类型冲突时停下修正，不重建表。
4. 为目标表保存有名称的本机连接：默认沿用个人全局 `~/.config/secret-book/.env`，展示实际路径、表和配置名，取得本地保存授权后执行 `config save`。同一未变化身份可复用已确认 token；第一套成为当前项，后续新增保留原当前项。
5. 共享权限在飞书真实权限入口安排，仅执行已授权的成员范围。交付表链接和成员连接说明，各成员以本人身份使用。

完成时报告表定位、身份、连接回读及实际验证范围。新表为空是正常状态；创建和保存连接不能证明协作者权限或写权限已经验证，不通过录入真实测试凭证探测权限。管理员取用记录同样受 `visible_to` 过滤。

## 凭证提供者／维护者

新增凭证按下方流程由 Agent 创建记录；用户明确只要飞书界面维护指导时，解释所需字段即可，本机未初始化不阻塞。

1. **沿用已明确的配置需求。** 按上方[明确配置需求](#明确配置需求)完成对象选择与分析，或整理用户选择提供的确切配置，形成 `name`、`service`、`purpose`、`secret`。无需重新询问已明确的对象或路径。
2. **展示并确认记录方案。** 两条路径均向用户展示四项候选内容；`secret` 展示实际键名和“已提供／待填写”状态，已提供的敏感值保持掩码。另核对已指定的业务账号、到期时间及可见人员范围。用户确认这组内容后再创建；内容变化时重新确认变化项。
3. **连接目标表。** 复用已明确的表和本人身份；需要首次连接时，以维护者本人 profile 登录并确认身份，用 `init-connect` 只读检查表结构与可见记录，再按明确授权保存本机连接。读取成功不代表有编辑权限。没有链接或权限时，由用户向管理员取得；用户明确要自建表才切换到管理员任务。
4. **创建一条记录。** 使用 `save` 一并写入已确认元数据、自动生成的编号和 `secret`；已提供的 Value 正常写入，未提供的 Value 保留为 `KEY=`，允许全部或部分键缺值。不能用“待填写”等文字、示例密钥或伪造值代替空值。需要受限人员名单时，创建动作必须一并落实已确认名单；人员身份尚未核实时先补齐，不能先创建无限制记录再补名单。
5. **把已有记录交给用户补值。** 创建成功后给出表／记录定位链接、记录名称和待补键名；请用户只在这条记录的 `secret` 中补上对应 `=` 后的 Value，保留键名与已有值。报告“记录已创建，以下值待补充，补齐后才能取用”，不能要求用户再新建记录、重填元数据或处理编号，也不能把创建成功描述为凭证可用或鉴权成功。Value 已全部提供时如实报告保存结果，仍不等于服务鉴权通过。

`list` 可列出待补记录，`get` 可查看键名及待补值状态；查看不要求先填写 Value。实际取用需要的值尚空时，引导维护者在原记录补齐，然后继续原取用目标。

已有记录内容的修改、删除和名单调整在飞书界面完成。历史记录缺 ID 时用 `repair-ids --name <唯一记录名>` 和本次表选择参数，先展示补齐摘要，确认后追加 `--confirm <token>`，仅补该记录的 ID。查询和取用不代做此动作；已存在 ID 时保持原值。成功后回读确认，结果不明时先检查已有 ID。

完成时只报告记录元数据和实际变更范围。仅提供指导时注明仍待用户在界面执行。凭证生成、轮换和吊销由原服务完成；表中值与使用者本机值分别更新，不自动通知成员或同步各机器。

## 凭证使用者

1. 为业务配置取值时先读 [业务配置流程](consumer-setup.md)，取得真实字段声明和实际加载器的无值来源报告。已可正常运行业务时无需初始化 Secret Book。
2. 用户确定从 Secret Book 取用后，取得已有表链接，使用本人 profile 登录并确认身份。用 `init-connect --url <表链接> --lark-profile <本人profile>` 检查表定位、字段及可见记录，状态 `connected_read_only` 后再经授权执行 `save_command` 保存本机连接；远端不建表、不补列、不补 ID。
3. 无链接时让用户取得已有表，或交回业务工具的本机手填分支。只有用户明确决定自建个人表，才切换管理员任务，完成后回到取用目标。
4. 缺列交管理员处理，缺 ID 交维护者处理。没有可见记录时只报告已知事实；缺记录与不可见无法区分时照实说明，不借用其他身份或改名单。
5. 确认记录、业务账号、表中实际 key 到业务字段的映射和目标文件，执行 `configure`。只有仅本轮、短期、明确不保存或目标不支持保存时才用 `run`；手工粘贴用 `copy`。

“只读”指远端令牌表，经确认的本机连接和业务配置仍可保存。分别报告连接、业务文件回读、实际生效来源、线上鉴权的结果；文件写入成功不等于鉴权成功，不授权重发原业务任务。表中轮换、默认连接或名单变化不更新也不收回已保存／复制的值。

## 业务 Skill／Plugin 接入开发者

1. 确定待接入产物及其真实配置格式，读取现有加载器与声明。没有令牌配置或飞书登录时继续本地工作。
2. 按 [业务声明与报告格式](consumer-setup.md#业务声明与报告格式) 声明真实 key、必填／可选、敏感性、准确默认值和关联组；让真实加载器输出无值来源报告，提供写后检查入口。
3. 用合成记录、模拟飞书响应与临时目录验证新增、修复原来源、映射、取消、确认恢复和来源变化。纯本地模拟不连接真实表或使用真实密钥。
4. 已明确范围的真实联调按使用者任务连接指定测试表；确需建测试表或写测试记录时，分别切换管理员／维护者并确认具体动作。
5. 业务后续直接读取本机配置。普通 dotenv 之外的格式由业务提供专用写入入口，不用每次 `run` 取值替代实现。

完成时分别报告本地契约测试、Claude Code／Codex／WorkBuddy 实际调用、真实服务鉴权。未验证的项目保持未验证，不为消除“未初始化”状态创建生产表。

## 恢复

任务状态只保留角色、识别依据、无密钥目标、实际宿主与运行环境、表／配置定位、阶段和待确认指纹。密钥、stdin、完整命令参数、飞书 `device_code` 和原始外部响应不写入任务状态。

续轮重新读取本文件和相应任务状态，再核对角色、目标、表、身份、实际配置来源及目标文件。本次配置依据（使用对象或确切配置要求）必须能追溯到用户的明确请求或选择；若旧任务只有 Agent 推断的 goal／basis，且没有对应用户依据，先回到“明确配置需求”，不沿用该猜测分析、查表或写入。已确认四项的确切配置路径仍可继续，不补问使用对象。另一任务、宿主、工作目录或安装不能直接消费原确认；输入改变则重新预览确认。待确认 token 的存在不能代替用户同意。

业务配置继续通过 `configure-status` 和 `consumer-configurations.json` 恢复参数与完整摘要；同一任务续接使用 `workflow status` 的确认 token，不把底层配置记录里的 token 直接当作任务 token。通用任务仅保留关联进度，不复制值或另做业务写入器。登录授权码只留在短期上下文；丢失、过期或续接失败按 SKILL.md 的 split-flow 处理。

写入前记录正在执行的动作。`verification_required` 表示中断或结果不明，先通过只读入口核对；新建表要在飞书确认实际创建结果，补列要重新检查字段，本机文件要回读。该任务保留写入标记，不直接重放或标为完成。核对实际结果后，以 `--outcome cancelled` 关闭旧待办，重新记录尚未完成的目标；已创建的表只做连接和配置保存。不能换一个任务 ID 绕过核对，再做同一次创建或写入。
